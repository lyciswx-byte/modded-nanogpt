# Record #92 on one NVIDIA GB10 (DGX Spark) — experimental port

This branch is based on `92-1xH100`, **not** the upstream eight-H100 baseline. It keeps the ANVIL optimizer, sampled softmax, hashed bigram/trigram embeddings, sparse-row Adam and CUDA-graph training design, while adding an **SM121/ARM64-specific Docker profile and operator backends**.

**Status: native GB10 operator bring-up and one default training run completed on 2026-10-17.** The run completed all 19,104 updates in 5,494.381 s of charged training time and reached validation CE **3.5956**, above the target **3.28**. This is not an official speedrun. The upstream record #92 ran on **8 H100 GPUs in 39.9 s**, and is not a timing target for one GB10.

## Hardware / software

- **GB10 (Grace Blackwell)**: `sm_121`, ARM64 Grace CPU, up to **128 GB CPU/GPU-coherent unified memory**, and substantially less memory bandwidth than H100. That 128 GB is **not** 128 GB of dedicated HBM and it is shared with the OS, CPU and Docker.
- Docker base: **`nvcr.io/nvidia/pytorch:26.09-py3`** (published NGC image, CUDA 13.4.1, PyTorch 2.14.0a0). This was the newest NVIDIA framework release located as of **2026-10-16**. We pin a dated release tag instead of `latest`. Before building, verify that the registry serves **linux/arm64** for that tag.
- Use a recent host driver that is compatible with CUDA 13.4.1, NVIDIA Container Toolkit, NVIDIA Docker runtime. Driver constraints follow NVIDIA's current compatibility guide; a CUDA toolkit *inside* Docker cannot repair an incompatible *host* driver.
- Dockerfile does **not** replace the base-image torch with the H100 branch's `torch==2.10/cu128` wheel. Replacing it is a common cause of wrong-architecture JIT or ABI failures.

The original [Dockerfile](Dockerfile) and [requirements.txt](requirements.txt) remain for the other branches. For GB10 always use [Dockerfile.gb10](Dockerfile.gb10) and [requirements.gb10.txt](requirements.gb10.txt).

## Build and run

On the **GB10 host**, clone this specific branch and check Docker's CPU platform and image availability:

```bash
git clone https://github.com/lyciswx-byte/modded-nanogpt.git
cd modded-nanogpt
git checkout 92-1xGB10

uname -m
nvidia-smi
docker buildx imagetools inspect nvcr.io/nvidia/pytorch:26.09-py3
docker build --platform linux/arm64 -f Dockerfile.gb10 -t modded-nanogpt:92-gb10 .
```

The registry manifest must include `linux/arm64`; do not use x86 emulation for CUDA execution. You may capture the pulled base image's digest with `docker image inspect` for strict reproducibility.

First run **real GPU operator checks**, before downloading FineWeb:

```bash
docker run --rm --gpus all --ipc=host --ulimit memlock=-1 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 python tools/gb10_kernel_probe.py --capture-attention
```

Only after the operator probe passes, fetch FineWeb and launch training:

```bash
docker run --rm --gpus all --ipc=host \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 python data/cached_fineweb10B.py 9

docker run --rm --gpus all --ipc=host --ulimit memlock=-1 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 bash run.sh
```

If you see an OOM or memory pressure, **reduce microbatch size first** (`GB10_MICROBATCH_DIVISOR=4`), then `VAL_BATCH_SIZE`, then (only if needed) `NGRAM_VOCAB_SIZE`. Docker cannot manufacture additional dedicated GPU memory.

## Operator adaptation matrix

| Component | Original H100 path | GB10 default | Further tests/choices |
|---|---|---|---|
| Causal variable-length sliding-window attention | checksum-pinned, H100-specific FA3 `sm90a` binary | **PyTorch FlexAttention** with GPU-derived document/block mask, no FA3 binary | `NANOGPT_ATTENTION_BACKEND=fa2` or `fa4` **opt-in**; must pass probe, support for sm121 is not assumed |
| Unequal QK and V head sizes (64 / 128) | patched FA3 | pad both to common width, preserve explicit softmax scale; slice output | CPU reference and GPU fwd/bwd probes; monitor kernel occupancy |
| MLP relu-square | FP8 TensorDescriptor/TMA Triton | **BF16 PyTorch F.linear + square**, native autograd; unused FP8 MLP quantization is skipped while retaining FP8 lm_head refresh | `GB10_MLP_BACKEND=fp8` experimental after `--check-fp8-mlp` |
| QKV projection | custom FP8 `torch._scaled_mm` + Triton rotary | retained | packed FP8 QKV + RoPE forward/backward reference checks, including paired heads and key offset, pass on GB10 |
| Logit head / sampled softmax | FP8 matmul, custom CE CUDA/Triton kernels | retained | actual full (50304) and sampled (10240/14336/24576) CE forward/backward reference checks pass; native-device NVRTC target replaces hardcoded sm90 |
| Hash n-gram lookup / sparse scatter Adam | Triton kernels + all-to-all owners | retained, single-rank communication bypass | ngram forward/backward plus repeated-row merge, row Adam commit and lazy moment replay checks pass |
| ANVIL and CUDA-graph capture | Hopper-tuned CUDA graphs | retained | compile, memory and capture tests must pass on GB10 |

**FlexAttention note:** The default builds block masks from each live batch's `cu_seqlens` on GPU. This preserves document boundaries and causal local windows including paired-head sequences (the original caller doubles the packed lengths). It can incur high mask-construction overhead and sizable compilation/CUDA-graph footprints at 24k-token microbatches. It is a functional portability baseline, not necessarily the fastest GB10 kernel. Once tested on a device, compare it against supported FA2/FA4 kernels, only with the same mask semantics and gradients.

**Why not FA3?** Its binary is compiled for Hopper/sm90a and cannot be safely dispatched on GB10/sm121. Do not spoof an SM90 architecture with `TRITON_OVERRIDE_ARCH`. The Dockerfile instead supplies CUDA 13's ptxas and `TORCH_CUDA_ARCH_LIST=12.0+PTX`; an SM121-native build should use that platform's verified compiler settings.

**FP8 MLP validation shared-memory fix:** The default GB10 MLP implementations
use standard BF16 `F.linear/ReLU/square/F.linear` when FP8 arguments are absent
(validation). The explicitly selected TMA implementation uses the adapted
SM121 tiles described below.
Previously `GB10_MLP_BACKEND=fp8` re-entered the Hopper
`linear_relu_square_kernel` during validation, which reproduced
`Required: 131072, Hardware limit: 101376` under Inductor even after its
automatic pipeline fallback. SM121 FP8 priming covers training variants only,
so it could not fix this BF16 variant. FP8 training dispatch remains unchanged.
Run the compiled regression check with each backend (`bf16`, `fp8`,
`fp8_sm121`):

```bash
docker run --rm --gpus all --ipc=host \
  -e NANOGPT_TARGET=gb10 -e GB10_MLP_BACKEND=fp8 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 python tools/gb10_kernel_probe.py --eval-mlp-only
```

The check uses the actual `GPT._mlp` dispatch under `torch.compile(fullgraph=True)`,
including 768→2816→768 projections, aligned/partial tiles and an 8192-token
batch, compared against FP32 math (relative L2 error < 0.03).

## SM121-specific FP8 MLP (experimental)

Two opt-in implementations are available: `GB10_MLP_BACKEND=fp8_sm121`
uses cuBLASLt FP8 GEMMs and SM121-tunable Triton quantize/transpose/amax
epilogues. Alternatively, `GB10_MLP_BACKEND=fp8` with
`GB10_FP8_MLP_IMPL=sm121` uses an SM121 pointer-based fused Triton FP8
GEMM/activation kernel with eager precompile tile tuning. Neither uses the
legacy Hopper TensorDescriptor/TMA path by default on GB10.
Default remains `bf16`.
For the numeric reference, `torch.compile` checks, six-tile speed sweep and
safe promotion criteria, see [SM121_FP8_MLP.md](SM121_FP8_MLP.md).
**The new backend has not yet been validated or benchmarked on GB10 hardware.**
The documented BF16 3.5956 CE run is not evidence for the new FP8 path.

### Adapted Hopper TMA MLP on GB10

`GB10_MLP_BACKEND=fp8 GB10_FP8_MLP_IMPL=hopper` selects the original fused
TensorDescriptor/TMA GEMM and epilogue, adapted for SM121. GB10 uses
`BLOCK_M=64`, `BLOCK_N=128`, `BLOCK_K=64`, 4 warps and one pipeline stage
for BF16 forward, FP8 forward and FP8 backward. H100 tile/pipeline defaults
are unchanged. No architecture override is used.

The measured compiler metadata shared-memory allocations are 32,768 bytes
(BF16 forward), 16,896 bytes (FP8 forward) and 8,200 bytes (FP8 backward),
all below the 101,376-byte GB10 limit. The conservative default is safe
before eager priming as well as inside `torch.compile` and CUDA Graph capture.

```bash
docker run --rm --gpus all --ipc=host \
  -e NANOGPT_TARGET=gb10 -e GB10_MLP_BACKEND=fp8 -e GB10_FP8_MLP_IMPL=hopper \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 python tools/gb10_tma_mlp_probe.py --bench
```

The probe checks the independent quantized FP8 forward/gradient contract,
partial tiles, folded gain gradients, delayed amax, compiled BF16 validation,
and CUDA Graph replay with live inputs. It is also included in
`tools/gb10_kernel_probe.py --capture-attention --check-fp8-mlp` with these flags.
To use it for training, pass the same environment variables to `bash run.sh`.
Default remains BF16; full-run quality/throughput have not been revalidated
for this TMA backend. See [native TMA checks](reports/gb10-2026-10-17/tma-mlp-sm121.md).

## Default training geometry (one GPU)

| Value | GB10 branch default |
|---|---:|
| training batch tokens per optimizer step, stage 0 / 1 / 2 / taper / extension | **8192 / 16384 / 24576 / 20480 / 8192** |
| scheduled + growth + extension steps | **17,952 + 832 + 320 = 19,104** |
| n-gram table | **10,575,360 rows × 768 BF16 ≈ 16.24 GB weights** + states |
| global validation batch | **131,072** tokens |
| validation target | FineWeb CE **≤ 3.28 (UNVERIFIED)** |

GB10 defaults use half the H100-port local microbatch and twice its step count to approximately preserve total training token exposure. This **does not reproduce** the original eight-GPU global batch, optimizer trajectory, or full 84.6M-row hash table (130 GB BF16 alone). The smaller table changes hash collisions and therefore training quality, which must be remeasured.

## Controls

- `NANOGPT_ATTENTION_BACKEND=flex` (default), `fa2`, `fa4`; `fa3` is blocked for `NANOGPT_TARGET=gb10`.
- `GB10_MLP_BACKEND=bf16` (default) or experimental `fp8`. The BF16 path may be slower, but does not require the original Hopper TMA GEMM path.
- `GB10_MICROBATCH_DIVISOR=2` (default), `1`, `4`, or `8`. This changes step geometry *and* default duration proportionally. Adjusting divisor changes training dynamics.
- `NGRAM_VOCAB_SIZE=10575360` by default on a single GPU (must be an even number >= 4).
- `VAL_BATCH_SIZE=131072` by default. Must divide `10485760`.
- `TRAIN_SEED`, `LR_SCALE`, `NUM_SCHEDULED_ITERATIONS`, `NUM_EXTENSION_ITERATIONS` inherited from the H100 port.

Use `docker run -e VARIABLE=value ...` to override environment values. Example to limit working memory at the cost of more optimizer updates:

```bash
docker run --rm --gpus all --ipc=host \
  -e GB10_MICROBATCH_DIVISOR=4 -e VAL_BATCH_SIZE=65536 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 bash run.sh
```

## Verification checklist

1. Docker image is linux/arm64; Python reports torch CUDA 13.x and compute capability (12,1).
2. `tools/gb10_kernel_probe.py` passes **attention forward+backward**, Triton JIT, scaled FP8 GEMM, BF16 MLP and n-gram lookup/grad sink. The probe alone does not exercise the full training step.
3. Complete `torch.compile` and CUDA-graph capture warmup succeeds on GB10. If this fails, record the kernel traceback and reduce batch size before choosing a different backend.
4. Training completes without nonfinite gradients, CPU/GPU memory exhaustion, or silent fallback to x86 binaries.
5. Final FineWeb validation cross-entropy <= 3.28 is observed; preserve the logs and measured time. Until then, describe it as **experimental**, not “reproduced”.

Native testing on 2026-10-17 confirmed ARM64, GB10 `(12,1)`, the ARM64 image manifest,
Docker build, and the expanded real operator probe (including compiled attention CUDA graph replay).
The default training result and exact reproduction commands are recorded in
[the GB10 execution report](reports/gb10-2026-10-17/README.md).

### Bounded training smoke configuration

Very short schedule overrides fail the existing tail-average assertion: total steps must be
at least `336*16 + 250 = 5626` with the default divisor. Use an even, bounded schedule that
also gives all six graph configurations enough warmup visits:

```bash
docker run --rm --gpus all --ipc=host --ulimit memlock=-1 \
  -e NUM_SCHEDULED_ITERATIONS=4800 -e NUM_EXTENSION_ITERATIONS=32 -e TRAIN_SEED=1234 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 bash run.sh
```

This runs `4800 + 832 + 32 = 5664` optimizer updates. It preserves one update per
microbatch, the default batch sizes and the full 10,485,760-token validation. Its shorter
schedule is a smoke test, not a default-run quality result.

For an isolated default-sized before/after refresh measurement, the operator probe supports
`--benchmark-refresh`. It times the old unused MLP quantization plus required lm_head
refresh versus the BF16-mode refresh, both eagerly and under CUDA graphs. This excludes
model forward/backward and ANVIL and must not be reported as training throughput.


### Optional training profile

`GB10_PROFILE_START` and `GB10_PROFILE_STEPS` enable one bounded CPU/CUDA profiling
window after warmup. The default `GB10_PROFILE_STEPS=0` leaves profiling disabled.
For example, `-e GB10_PROFILE_START=11000 -e GB10_PROFILE_STEPS=8` samples stage 2
of the default schedule. Each rank writes `logs/<run-id>.rank<rank>.profile.json`
and its run log includes a kernel-time table. Graph launches, H2D activity and
host overhead can be inspected in the trace. These diagnostic runs include
profiling overhead in the reported training time; compare clean timing runs
only with identical seeds, token budgets and configuration.


### NGC dependency metadata limitation

`python -m pip check` exits 1 in both the untouched NGC 26.09 base and the project
image, with the same four findings: `triton-kernels` requests missing `pytest`,
`cupti-python` requests missing `nvidia-cuda-cupti` wheel metadata, `quack-kernels`
requests CUTLASS DSL 4.6.1, and `flash-attn-4` requests CUTLASS DSL 4.6.0.dev0 while
the base supplies 4.8.0.dev0. The default Flex/Triton/FP8 paths and an actual
CUDA-graph CUPTI trace executed successfully despite those metadata findings.
Do not describe the whole image as passing dependency consistency checks.
FA4 and quack backends remain unvalidated; no framework/CUTLASS replacement was
made to silence warnings from unused optional backends.


### Explicit CE correctness correction

The original fused CE forward truncates multi-token predictions at a microbatch's
end, but its backward incorrectly included weights of missing future targets in
the softmax-normalizer gradient. A direct three-target test measured about 1.75x
the expected non-target gradient on the last row. The shared full/sampled CE
kernel now accumulates only existing targets' weights. Forward losses, token
batches, update counts and optimizer cadence are unchanged; the old erroneous
boundary gradients are intentionally corrected. The native probe checks all
four vocabulary widths and 1/2/3 targets against autograd, with repeated targets
and prefix loss. This is a documented correctness exception to preserving the
old numerical trajectory.


## SM121 FP8 MLP candidates: compatibility versus GB10 optimization

The completed 2026-10-17 **19,104-step** baseline used
\`GB10_MLP_BACKEND=bf16\`; its validation CE **3.5956** is **not** an FP8
MLP result. FP8 experiments are opt-in, and changing them requires new
validation of forward/backward, compile and graph capture, and full convergence.

Two alternative non-Hopper implementations now exist, with deliberately
separate configuration and benchmark paths:

| Profile | Computation | Tuning scope |
|---|---|---|
| \`GB10_MLP_BACKEND=fp8_sm121\` | SM121-compatible cuBLASLt FP8 GEMMs followed by separate Triton ReLU-square / dpre + quantize/transposed-store epilogues | Epilogue \`GB10_FP8_MLP_TILE_M\` (16/32/64), \`GB10_FP8_MLP_TILE_N\` (64/128); run \`tools/gb10_fp8_mlp_probe.py --sweep --tokens 8192\` |
| \`GB10_MLP_BACKEND=fp8\` + \`GB10_FP8_MLP_IMPL=sm121\` | Descriptor-free Triton \`tl.dot\` FP8 GEMMs, with activation/dpre and both FP8 output layouts fused into the same kernel | Kernel \`M/N/K\` tile, warp count and pipeline stages; eager CUDA-graph kernel autotuning before \`torch.compile\` (\`GB10_FP8_MLP_AUTOTUNE=1\`) |
| \`GB10_MLP_BACKEND=bf16\` | Standard PyTorch BF16 MLP | Known working fallback |

**Neither experimental FP8 variant is proven faster on a GB10 yet.**
The cuBLASLt variant is a safer and valuable architecture-independent FP8
correctness baseline; it still materializes intermediate BF16 pre/dpost
tensors. The Triton variant removes those intermediate round trips and can
use shape-dependent tiles, but may suffer from less efficient FP8 tensor-core
scheduling than cuBLASLt. Actual SM121 timing, correctness and memory
profiling—not fusion alone—determine the winner.

To run the fused Triton variant on a **physical GB10**, after rebuilding
\`Dockerfile.gb10\`:

```bash
docker run --rm --gpus all --ipc=host --ulimit memlock=-1 \
  -e GB10_MLP_BACKEND=fp8 -e GB10_FP8_MLP_IMPL=sm121 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 python tools/gb10_fp8_mlp_bench.py --benchmark --tokens 8192
```

For the cuBLASLt variant:

```bash
docker run --rm --gpus all --ipc=host --ulimit memlock=-1 \
  -e GB10_MLP_BACKEND=fp8_sm121 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 python tools/gb10_fp8_mlp_probe.py --check-compile --bench --tokens 8192
```

Both routes reuse the original MLP FP8 caches, activation scales, 
delayed amax and weight-refresh cadence. They do **not** introduce gradient
accumulation or change the small-batch training schedule. For any experimental
failure, run with \`GB10_MLP_BACKEND=bf16\` to return to the tested baseline.
Operator-only timings are not end-to-end training throughput. These GPU commands
have not been executed or benchmarked as part of this addition.
