# Record #92 on one NVIDIA GB10 (DGX Spark) — experimental port

This branch is based on `92-1xH100`, **not** the upstream eight-H100 baseline. It keeps the ANVIL optimizer, sampled softmax, hashed bigram/trigram embeddings, sparse-row Adam and CUDA-graph training design, while adding an **SM121/ARM64-specific Docker profile and operator backends**.

**Status: code committed; no physical GB10 has been used to validate kernels or training.** It is not an official speedrun and **neither final FineWeb CE <= 3.28 nor training time has been demonstrated**. The upstream record #92 ran on **8 H100 GPUs in 39.9 s**, and is not a timing target for one GB10.

## Hardware / software

- **GB10 (Grace Blackwell)**: `sm_121`, ARM64 Grace CPU, up to **128 GB CPU/GPU-coherent unified memory**, and substantially less memory bandwidth than H100. That 128 GB is **not** 128 GB of dedicated HBM and it is shared with the OS, CPU and Docker.
- Docker base: **`nvcr.io/nvidia/pytorch:26.09-py3`** (published NGC image, CUDA 13.4.1, PyTorch 2.14.0a0). This was the newest NVIDIA framework release located as of **2026-10-16**. We pin a dated release tag instead of `latest`. Before building, verify that the registry serves **linux/arm64** for that tag.
- Use a recent host driver that is compatible with CUDA 13.4.1, NVIDIA Container Toolkit, NVIDIA Docker runtime. Driver constraints follow NVIDIA's current compatibility guide; a CUDA toolkit *inside* Docker cannot repair an incompatible *host* driver.
- Dockerfile does **not** replace the base-image torch with the H100 branch's `torch==2.10/cu128` wheel. Replacing it is a common cause of wrong-architecture JIT or ABI failures.

The original [Dockerfile](Dockerfile) and [requirements.txt](requirements.txt) remain for the other branches. For GB10 always use [Dockerfile.gb10](Dockerfile.gb10) and [requirements.gb10.txt](requirements.gb10.txt).

## Build and run

On the **GB10 host**, clone this specific branch and check Docker's CPU platform and image availability:

```bash
git clone https://github.com/lyciswx-byte/modded-nanogpt.git
cd modded-nanogpt
git checkout 92-1xGB10

uname -m
nvidia-smi
docker buildx imagetools inspect nvcr.io/nvidia/pytorch:26.09-py3
docker build --platform linux/arm64 -f Dockerfile.gb10 -t modded-nanogpt:92-gb10 .
```

The registry manifest must include `linux/arm64`; do not use x86 emulation for CUDA execution. You may capture the pulled base image's digest with `docker image inspect` for strict reproducibility.

First run **real GPU operator checks**, before downloading FineWeb:

```bash
docker run --rm --gpus all --ipc=host --ulimit memlock=-1 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 python tools/gb10_kernel_probe.py
```

Only after the operator probe passes, fetch FineWeb and launch training:

```bash
docker run --rm --gpus all --ipc=host \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 python data/cached_fineweb10B.py 9

docker run --rm --gpus all --ipc=host --ulimit memlock=-1 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 bash run.sh
```

If you see an OOM or memory pressure, **reduce microbatch size first** (`GB10_MICROBATCH_DIVISOR=4`), then `VAL_BATCH_SIZE`, then (only if needed) `NGRAM_VOCAB_SIZE`. Docker cannot manufacture additional dedicated GPU memory.

## Operator adaptation matrix

| Component | Original H100 path | GB10 default | Further tests/choices |
|---|---|---|---|
| Causal variable-length sliding-window attention | checksum-pinned, H100-specific FA3 `sm90a` binary | **PyTorch FlexAttention** with GPU-derived document/block mask, no FA3 binary | `NANOGPT_ATTENTION_BACKEND=fa2` or `fa4` **opt-in**; must pass probe, support for sm121 is not assumed |
| Unequal QK and V head sizes (64 / 128) | patched FA3 | pad both to common width, preserve explicit softmax scale; slice output | CPU reference and GPU fwd/bwd probes; monitor kernel occupancy |
| MLP relu-square | FP8 TensorDescriptor/TMA Triton | **BF16 PyTorch F.linear + square**, native autograd | `GB10_MLP_BACKEND=fp8` experimental after `--check-fp8-mlp` |
| QKV projection | custom FP8 `torch._scaled_mm` + Triton rotary | retained | GPU FP8 GEMM probe; the full QKV custom op remains unverified |
| Logit head / sampled softmax | FP8 matmul, custom CE CUDA/Triton kernels | retained | probe checks CUDA compile API; full forward/backward training still required |
| Hash n-gram lookup / sparse scatter Adam | Triton kernels + all-to-all owners | retained, single-rank communication bypass | ngram forward/backward probe; full sparse update remains unverified |
| ANVIL and CUDA-graph capture | Hopper-tuned CUDA graphs | retained | compile, memory and capture tests must pass on GB10 |

**FlexAttention note:** The default builds block masks from each live batch's `cu_seqlens` on GPU. This preserves document boundaries and causal local windows including paired-head sequences (the original caller doubles the packed lengths). It can incur high mask-construction overhead and sizable compilation/CUDA-graph footprints at 24k-token microbatches. It is a functional portability baseline, not necessarily the fastest GB10 kernel. Once tested on a device, compare it against supported FA2/FA4 kernels, only with the same mask semantics and gradients.

**Why not FA3?** Its binary is compiled for Hopper/sm90a and cannot be safely dispatched on GB10/sm121. Do not spoof an SM90 architecture with `TRITON_OVERRIDE_ARCH`. The Dockerfile instead supplies CUDA 13's ptxas and `TORCH_CUDA_ARCH_LIST=12.0+PTX`; an SM121-native build should use that platform's verified compiler settings.

See [GB10_GRADIENT_ACCUMULATION.md](GB10_GRADIENT_ACCUMULATION.md) for the
precise 8-rank effective-batch sizes, 16-microbatch/optimizer-update
arithmetic, optimizer-step schedules, CUDA-graph changes, and sparse-gradient
blockers. The CPU reference math is in
[tools/gb10_grad_accum_reference.py](tools/gb10_grad_accum_reference.py).

**Not yet enabled in `run.sh`.** The current run performs optimizer updates
after **each** small batch; its 19,104 steps approximate token exposure but
are not eight-H100-equivalent gradient accumulation.

## Default training geometry (one GPU)

| Value | GB10 branch default |
|---|---:|
| training batch tokens per optimizer step, stage 0 / 1 / 2 / taper / extension | **8192 / 16384 / 24576 / 20480 / 8192** |
| scheduled + growth + extension steps | **17,952 + 832 + 320 = 19,104** |
| n-gram table | **10,575,360 rows × 768 BF16 ≈ 16.24 GB weights** + states |
| global validation batch | **131,072** tokens |
| validation target | FineWeb CE **≤ 3.28 (UNVERIFIED)** |

GB10 defaults use half the H100-port local microbatch and twice its step count to approximately preserve total training token exposure. This **does not reproduce** the original eight-GPU global batch, optimizer trajectory, or full 84.6M-row hash table (130 GB BF16 alone). The smaller table changes hash collisions and therefore training quality, which must be remeasured.

## Controls

- `NANOGPT_ATTENTION_BACKEND=flex` (default), `fa2`, `fa4`; `fa3` is blocked for `NANOGPT_TARGET=gb10`.
- `GB10_MLP_BACKEND=bf16` (default) or experimental `fp8`. The BF16 path may be slower, but does not require the original Hopper TMA GEMM path.
- `GB10_MICROBATCH_DIVISOR=2` (default), `1`, `4`, or `8`. This changes step geometry *and* default duration proportionally. Adjusting divisor changes training dynamics.
- `NGRAM_VOCAB_SIZE=10575360` by default on a single GPU (must be an even number >= 4).
- `VAL_BATCH_SIZE=131072` by default. Must divide `10485760`.
- `TRAIN_SEED`, `LR_SCALE`, `NUM_SCHEDULED_ITERATIONS`, `NUM_EXTENSION_ITERATIONS` inherited from the H100 port.

Use `docker run -e VARIABLE=value ...` to override environment values. Example to limit working memory at the cost of more optimizer updates:

```bash
docker run --rm --gpus all --ipc=host \
  -e GB10_MICROBATCH_DIVISOR=4 -e VAL_BATCH_SIZE=65536 \
  -v "$PWD:/workspace/modded-nanogpt" -w /workspace/modded-nanogpt \
  modded-nanogpt:92-gb10 bash run.sh
```

## Verification checklist

1. Docker image is linux/arm64; Python reports torch CUDA 13.x and compute capability (12,1).
2. `tools/gb10_kernel_probe.py` passes **attention forward+backward**, Triton JIT, scaled FP8 GEMM, BF16 MLP and n-gram lookup/grad sink. The probe alone does not exercise the full training step.
3. Complete `torch.compile` and CUDA-graph capture warmup succeeds on GB10. If this fails, record the kernel traceback and reduce batch size before choosing a different backend.
4. Training completes without nonfinite gradients, CPU/GPU memory exhaustion, or silent fallback to x86 binaries.
5. Final FineWeb validation cross-entropy <= 3.28 is observed; preserve the logs and measured time. Until then, describe it as **experimental**, not “reproduced”.

The code and Docker specification were written without direct access to a GB10 machine: none of steps 1–5 is claimed to have passed on hardware.
